# ทีม 1 — ระบบ log → knowledge (cyber security)

*ชื่อโครงงานถอดไม่ได้ ผมเรียกตามเนื้อหา · ทีมบอกว่าอยู่ในช่วง concept ต้นโปรเจค (ทำจริง)*

**ทำอะไร**: เว็บแอปรวม log ของ network / firewall → ให้ AI วิเคราะห์เป็น case study พร้อมวิธีรับมือเบื้องต้น → **ผู้เชี่ยวชาญตรวจอนุมัติ** → ตรวจว่าเป็นหมวดใหม่หรือเติมในหมวดเดิม → เก็บเข้า knowledge management ให้คนค้นหาและนำกลับมาใช้

**Pain point**: log เป็นข้อมูลดิบ ซับซ้อน มาจากหลายแหล่ง ค้นยาก จัดหมวดไม่เป็นระบบ วิเคราะห์ด้วยคนใช้เวลานาน · เจอจากเพื่อนที่ฝึกงานสาย cyber security แล้วต้องรอ support นานเพราะขาดข้อมูลเก่า

**Challenge ที่ทีมระบุ**: ทำให้ AI แม่นยำ · ต้องมีคนอยู่ใน loop (กัน AI หลอน) → ต้องหาผู้เชี่ยวชาญมา approve · ทำให้ log อ่านเข้าใจง่ายสำหรับคนไม่มีพื้นฐาน

**Scope**: เว็บแอป (ไม่ทำ native) · In: อัปโหลดหลายประเภท, AI วิเคราะห์อัตโนมัติ, ผู้เชี่ยวชาญอนุมัติ, เข้าระบบ KM · Out: log ชนิดอื่นนอกจาก firewall/network

**คำถามกรรมการ → คำตอบ**

| คำถาม / ข้อสังเกต | คำตอบ / ผลลัพธ์ |
|---|---|
| ใช้ AI ตัวไหน? log ของหน่วยงานมักมีชั้นความลับ (เพื่อนฝึกงานที่กรมทหารเรือ) โยนให้ cloud ไม่ได้ จะใช้ local model ไหม แล้วฮาร์ดแวร์พอไหม | กำลังศึกษา **Ollama (local)** ข้อดีไม่มี rate limit ข้อเสียกิน GPU · อีกทางเป็นโมเดลฟรี (ถอดชื่อไม่ชัด) รันบนสเปคต่ำได้แต่ช้า · งบจำกัด |
| ภาพปลายทางยังไม่ชัด — "internal knowledge" หน้าตาเป็นยังไง ใครอ่าน อ่านแล้วเอาไปทำอะไร | ตอบว่าตั้งใจให้พนักงานทั่วไปในองค์กรอ่านเข้าใจง่าย · กรรมการให้ **กำหนด template (ปัญหา / วิธีแก้) และระบุว่าใครอ่านเพื่อทำอะไร** (ยกตัวอย่างบริษัทที่ใช้ KB template ให้ tech support) |
| ผู้ใช้แก้ปัญหาตามแล้วจะมี feedback / lessons learned กลับมาไหม | **ยังไม่ได้คิด** (กรรมการบอกว่าอาจต้องสัมพันธ์กับ ISO) |
| KM มีหลายระดับ ต้องประกาศให้ชัดว่าเป็น KM แบบไหน | ทีมรับทราบ (กรรมการเตือนว่า process ถัดไปอาจารย์อาจยิงประเด็นนี้) |
| Pain point "อ่านยาก" ยังไม่คม ต้องบอกว่ากระทบอะไร (เช่น เสียเวลาวันละ 2 ชม.) และ solution ลดเวลานั้นได้จริงไหม | แนะนำให้ไปลอง validate เพิ่ม |
| **ทำ mock-up** ให้เห็นภาพปลายทาง ไม่งั้นคนฟัง (นักลงทุน/กรรมการ/ลูกค้า) นึกไม่ออกว่าจบที่ไหน | ทีมรับทราบ |

**บทเรียนจากทีมนี้**: โดนถามหนัก 3 เรื่อง คือ *ข้อมูลลับกับ AI cloud · ปลายทางใครใช้ทำอะไร · pain point ไม่คม* — เรื่องที่ 2 และ 3 ตรงกับที่ Connecta ถูกถามด้วย

# ทีม 2 — Agentic AI วิเคราะห์ root cause ของ incident

*ชื่อโครงงานถอดได้ไม่ชัด (มีคำว่า Agentic AI, Root Cause, Incident) · กลุ่มผู้ใช้: ทีม operation / SRE / dev ที่เฝ้าระบบ*

**ทำอะไร**: เมื่อระบบล่ม ให้ AI agent รวบรวมข้อมูล **log + metrics + trace** ที่กระจายอยู่คนละที่ ผูกกันด้วย trace ID → วิเคราะห์หาสาเหตุ → สรุปและแนะนำวิธีแก้ → **คนเป็นผู้อนุมัติ** ก่อนให้ AI แก้ → ออก incident report · มีเว็บเดียวให้ทีม dev / SRE / ops เห็นเรื่องเดียวกัน · SRE ให้คะแนนว่า root cause ที่ AI วิเคราะห์ตรงกับหน้างานแค่ไหน (loop ปรับปรุง)

**Pain point (จากประสบการณ์ฝึกงานธนาคาร)**: ระบบล่มตี 3 ทีมเพิ่งรู้ตอนตี 5 แก้เสร็จ 8 โมง (>5 ชม.) เวลาส่วนใหญ่หายไปกับ "รอให้คนรู้" และ "หาสาเหตุ" ไม่ใช่การแก้ · service เพิ่มขึ้น ต้องเพิ่มคนเฝ้า (ยกตัวอย่าง LINE MAN 7 service) · การหา incident ด้วยมือ (ต้องเขียน query จากที่เก็บ log) เฉลี่ย **45 นาที** · incident ส่วนใหญ่เกิดหลัง deploy/migration ย้อนหา commit ยาก · ทีมส่งงานกันไปมา

**Challenge**: ไม่รู้ว่าระบบล่มตอนไหน (rate detection) · log / metric / trace เก็บแยกที่ ร้อยเรียงยาก · ต้องวิเคราะห์ด้วยมือ · คน operation เพิ่มตามจำนวน service

**วิธีที่ใช้**: connector แบบ OpenTelemetry · Prometheus (metrics), Loki (logs), Tempo (traces) · แจ้งเตือนผ่าน MS Teams / Slack / อีเมล · **ไม่แตะ source code ลูกค้า** และไม่ให้ AI ทำงานอัตโนมัติเต็มรูปแบบ (ต้องมีคน approve) · ใช้ dataset ของ incident ที่เคยใช้ในงาน conference ปี 2026 (บน microservice แบบมาตรฐาน) เพื่อทดสอบเทียบกับแพลตฟอร์มอื่น

**คำถามกรรมการ → คำตอบ**

| คำถาม / ข้อสังเกต | คำตอบ / ผลลัพธ์ |
|---|---|
| ใช้ AI ตัวไหน/รันที่ไหน — ถ้าใช้ dataset นี้ต้องผูกกับ cloud ไหม | ใช้ **local model** · กรรมการ: ระวังค่าใช้จ่ายฮาร์ดแวร์ |
| ไอเดียคล้ายซอฟต์แวร์ที่มีในตลาด (SIEM / Dynatrace) แล้วต่างยังไง? Dynatrace/SIEM ก็เริ่มมี agent จัดการ incident และแจ้งเตือนไปทางที่ตั้งไว้ | ทีมตอบว่า Dynatrace เห็นเป็น **metric** เป็นหลัก ถ้าจะดู log ของแอปต้องต่อ service เพิ่ม · ของทีมใช้ agent ตัวเดียวดึง log + metric + trace ผูกด้วย trace ID เห็นว่าตอน CPU 90% แอปทำอะไรอยู่ · กรรมการ: **แนวคิดโอเค แต่ฝากเรื่อง "ความเสี่ยงที่คล้าย SIEM" ไว้** ผู้พัฒนา SIEM ก็แปะ connector ได้เหมือนกัน · ทีมยอมรับว่าตอนแรกตั้งใจ *predict ล่วงหน้า 10 วัน* แต่ตัดทิ้งเพราะเวลา/งบ เหลือแค่ detection → "ไปคิดต่อว่าจะต่างยังไง" |
| ถ้าเกิด 2 incident พร้อมกัน (โอนเงิน vs แคมเปญ Double Day) มี priority ไหม | ทีมใส่ index ว่า log มาจาก service ไหน แยกเรื่องได้ · **จัดลำดับตาม business impact ยังไม่ได้ทำ ตั้งเป็น improvement ต่อ** |
| connector เชื่อมกับแต่ละ server/service ยังไง | ใช้ OTel collector วางเป็น sidecar ใน container ของแต่ละ service ตั้ง endpoint ให้ส่งไป Prometheus/Loki/Tempo |
| แจ้งเตือนอย่างเดียวไม่พอ ถ้าไม่มีคนดู Grafana ก็ไม่ตอบ pain point · และ **alert เยอะ (false alarm) จนคนเลิกสนใจ** จะทำยังไง | ส่ง notification ไปช่องทางที่องค์กรใช้ (Slack/Teams/อีเมล/โทรอัตโนมัติ) · ใช้ AI **คัดกรอง**: เมื่อมี alert CPU 90% ให้ไปดู log ของแอปก่อน ถ้ายังตอบ 200/ต่อ DB ได้ ไม่ถือเป็น incident จนกว่าจะเริ่ม 5xx |
| ข้อสังเกต | กรรมการเห็นว่า incident report ที่ AI สรุป ช่วยบริษัทที่ต้องทำ **ISO 27001 / audit** ได้มาก |

# ทีม 3 — ระบบจัดการสโมสรนักศึกษา SIT

*ชื่อภาษาอังกฤษถอดไม่ชัด ("... Management System for Student Association") · กลุ่มผู้ใช้: staff การเงิน/คณะกรรมการ/ที่ปรึกษาของสโมสรนักศึกษา SIT · เว็บแอป*

**ทำอะไร**: ศูนย์กลางข้อมูลของสโมสร — สต็อก/ออเดอร์ (พรีออเดอร์เสื้อ ฯลฯ) · งบประมาณรายโครงการ · บันทึกการเงิน · dashboard และการพยากรณ์ยอดขาย

**Pain point**: ข้อมูลเก็บกระจายหลายชีท · สต็อกลดด้วยมือ ไม่รู้ว่าเหลือจริงเท่าไร · ต้องตรวจสลิปกับยอดเงินด้วยมือ (manual reconcile) · ติดตามงบแต่ละโครงการยาก

**Challenge**: ตรวจสลิปกับยอด · **กฎของสโมสรเปลี่ยนทุกปี** ต้องยืดหยุ่น · ข้อมูลการเงินต้องคุมสิทธิ์ · **สมาชิกใหม่เข้ามาทุกปี** (adoption)

**วิธี**: reconcile สลิป (OCR) กับยอดเงิน + ตรวจ transaction · config ยืดหยุ่นตามกฎใหม่ · role + login + audit log · รองรับ import Google Sheet (ฟอร์มพรีออเดอร์)

**Outcome ที่คาด**: ดูข้อมูลจากแหล่งเดียว · ตามรอย transaction ถึงหลักฐาน · ตัดสินใจเรื่องงบเร็วขึ้น · มีข้อมูลย้อนหลังให้กรรมการรุ่นต่อไปวางแผน

**Scope**: In: inventory · order · project budget · financial recording · dashboard/forecast / Out: native mobile · เชื่อมธนาคาร (ต้องเป็นบริษัท) · เชื่อม NewAcis ของมหาลัย (ไม่มี public API) · payroll/tax

**คำถามกรรมการ → คำตอบ**

| คำถาม / ข้อสังเกต | คำตอบ / ผลลัพธ์ |
|---|---|
| สลิปปลอม/สลิปซ้ำ (เอาสลิปคนอื่นมาใช้) OCR ตรวจได้ไหม | ดู reference/วันที่ของสลิป · กรณีชื่อผู้โอนไม่ตรงกับผู้สั่ง (เช่น นักศึกษาต่างชาติใช้บัญชีเพื่อน) **ไม่ซีเรียส** |
| (กรรมการสายบัญชี) ยอดเท่ากัน เวลาเดียวกัน แยกไม่ออกว่า transaction จริงไหมถ้าไม่ดู **bank statement** · automation เต็มต้องต่อ API ธนาคารซึ่งต้องเป็นบริษัท | ทีมยืนยันว่าตั้งใจ 2 ขั้น: OCR สลิปอัตโนมัติ → **ปิดรอบพรีออเดอร์แล้วเทียบ bank statement อีกครั้ง** · รองรับ manual reconcile (ไฟล์ statement แบบ MT940) |
| ถ้าขายของอย่างอื่น ผู้ใช้ใหม่ๆ จะรู้ได้ยังไงว่าต้องทำฟอร์มแบบไหนให้ AI อ่านได้ (ตอนนี้ 1 Google Form ต่อ 1 สินค้า) | ต้องมี **master สินค้าในระบบก่อน** แล้วอัปโหลด template คำสั่งซื้อ · กรรมการ: ต้องคิดให้คนรุ่นหลังใช้ต่อได้ ไม่ใช่แค่ทีมเอง |
| ฟีเจอร์ตรวจสลิปเป็นกี่ % ของโปรเจก (เหมือนเป็นแค่ส่วนเล็ก) | ทีมยอมรับว่าประมาณ **1/10** ของโปรเจก · กรรมการ: จุดโฟกัสจริงควรเป็น **inventory / budget / การเงินภายใน** ไม่ใช่ฟีเจอร์ขายของ — ฟังแล้ว scope ไม่ชัด (ตอนแรกพูดถึง inventory แต่กลางเรื่องพูดถึงขายเสื้อ) |
| ⭐ ข้อแนะนำด้านบัญชี | inventory ต้องดุล "ของ" กับ "เงิน" · ควร**แยกของที่ซื้อมาขาย** (มีกำไร) ออกจาก**ของใช้ภายใน** (เป็นค่าใช้จ่าย) และแยกเป็น warehouse module กับ sales module ที่เชื่อมกัน ไม่ควรรวมกัน (ตัวอย่าง: หมวกที่ต้นทุน 200 ขาย 500 ถ้าเบิกไปใช้ในกิจกรรม ต้องประกาศว่าไม่ใช่สินค้าแล้ว ไม่งั้นตัวเลขไม่ดุล) · บริการเช็กสลิปของ third party มีค่าใช้จ่าย ~1–2 บาท/ใบ ซื้อขายสินค้ารวมเข้าต้นทุนได้ แต่ค่าใช้จ่ายภายในทำไม่ได้ |
| ⚠️ ความเสี่ยงเรื่อง policy | ระบบอาจดี แต่ถ้าอาจารย์ให้ทดลองใช้จริงกับสโมสร ปัญหาที่แท้อาจเป็น **นโยบาย/วิธีทำงาน** (เช่น คนหน้างานไม่รู้ว่าของชิ้นไหนถูกจองแล้ว) ไม่ใช่ที่ระบบ → อาจฉุดคะแนนถ้าวัดผลแล้วไม่แก้ปัญหา · ทีมตอบว่าปัญหาจริงคือกระบวนการหลังบ้านที่ไม่ชัด ต้องเขียนข้อกำหนดให้เข้ม |
| กฎสโมสรเปลี่ยนทุกปี เปลี่ยนแค่ไหน กระทบระบบยังไง | ส่วนใหญ่กระทบ **งบโครงการ** (เช่น เพดานเงินรางวัลกิจกรรม 3,000 → 5,000) และการเบิกเงินที่สโมสรทดรองจ่ายก่อน · กรรมการ: อธิบายด้วยตัวอย่างนี้ — **จะเห็นว่าเป็นแค่ config ของงบประจำปี ไม่ต้องพัฒนาใหม่** ถ้าอธิบายไม่ชัดจะดูเหมือน requirement เปลี่ยนจนต้อง redesign |
| ภาพรวม | กรรมการลังเลว่า main จริงคือ **สต็อก + งบ + การเงินภายใน** · แนะนำให้ควบคุม scope: โฟกัสว่า *มีงบเข้ามาเท่าไร โครงการไหนใช้เท่าไร ซื้ออะไรไปแล้ว มีสลิปไหม PO ตรงกับของที่ได้รับไหม สต็อกถูกตัดไปใช้แล้วหรือยัง* โดยยังไม่ต้องสนว่าเอาไปใช้หรือขาย → เมื่อเคลียร์แล้วค่อยเพิ่มโมดูลขายทีหลัง |
