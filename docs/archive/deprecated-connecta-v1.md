# 4. กฎที่กระทบการทำงานโดยตรง

## ⚠️ 4.1 ต้อง deploy ขึ้น server จริงภายใน 30 พ.ย.
> "พัฒนาอย่างน้อย 1 core feature (Frontend → Backend → DB) ที่ติดตั้งแล้วบน Server **ไม่อยู่ใน localhost**"

**ผลกระทบต่อแผนของเรา**: การ deploy ไม่ใช่เรื่องที่เลื่อนไปทำทีหลังได้ — มันคือเงื่อนไขให้คะแนน
→ **spike C0 (ตรวจสอบ VM) จึงเร่งด่วนกว่าที่ประเมินไว้** เพราะ lead time ของฝ่าย IT อาจเป็นสัปดาห์
→ ทำ CI/CD หรืออย่างน้อย deploy script ตั้งแต่เนิ่นๆ อย่ารอเดือนสุดท้าย

## ⚠️ 4.2 นิยาม "core feature" และสิ่งที่โชว์ได้ก่อนถึง voice/audio

> "การทำ feature login **ไม่ถือเป็น core feature** ของระบบทั่วไป ยกเว้นถ้าโครงงานนั้นทำระบบ Authentication"

**Exam 3 (30 พ.ย.) มีน้ำหนักส่วน core feature อยู่ 13 คะแนนจาก 35 (~ไม่ถึงครึ่งของ Exam นั้น) และเป็นแค่ระดับ "Release 1"** ไม่ต้องมี proximity audio ให้ทันตอนนี้ — สิ่งที่โชว์ได้และเพียงพอสำหรับรอบนี้คือ:

> **หน้าเว็บ → login (OAuth) → สร้างงาน (create event) → ลงทะเบียนเข้างาน → เข้าไปในโลก 2D → เห็นแมปที่ทำจาก Tiled → ตัวละครเดินได้**

นี่คือ flow **Frontend → Backend → DB** ครบ (สร้างงาน = เขียน DB, เข้าห้อง = อ่าน DB + realtime sync) โดยยังไม่ต้องแตะ WebRTC เลย ตรงกับที่บันไดแผนสำรอง (หัวข้อ 15) วางไว้อยู่แล้วว่าควรทำส่วนที่ไม่ใช้เสียงให้เสร็จก่อน

**ระบบคิว 1:1 ยังเป็น core feature ที่ควรใส่เพิ่มถ้าเวลาพอ** เพราะมี Test Case/Exception Handling ให้เขียนเยอะ (จองซ้ำพร้อมกัน, timer หมด, คนหลุดเน็ต) ซึ่งตรงกับเกณฑ์ 7 คะแนนของ Exam 3 โดยตรง — แต่ไม่ใช่เงื่อนไขบังคับสำหรับรอบนี้

## 4.3 AI Features เป็นเกณฑ์: Low / Intermediate / Advance
วิชาส่งเสริม "การใช้งาน AI ในแบบมืออาชีพ" แยกเป็น AI Tools (ช่วยพัฒนา) กับ AI Features (ในตัวระบบ)
**AI Features ของเรา**: booth bot แบบ RAG · AI matchmaking · (อาจเพิ่ม live transcription/แปลไทย-อังกฤษ)
→ RAG น่าจะจัดเป็น Intermediate–Advance ได้ ควรอธิบายให้ชัดว่าทำไมไม่ใช่แค่เรียก API

# 6. Pain point และจุดยืน

## Pain point ที่เก็บมา
- **ฝั่งผู้จัด**: ค่าเช่าสถานที่ · จ้าง staff · ค่า PR ออนไซต์ · เสียเวลาจัดงาน · การบริหารจัดการยุ่งยาก
- **ฝั่งผู้เข้าร่วม**: ติดปัญหาเวลาและระยะทาง
- ⭐ **ข้อที่สำคัญที่สุด**: ผู้เข้าร่วมออนไลน์ไม่ได้ connection เท่าคนมาออนไซต์ — โดยเฉพาะ *"อยากคุยตัวต่อตัวกับ speaker ก็ทำไม่ได้ นอกจากขอนัดนอกรอบ ซึ่งก็เป็นเรื่องลำบากของ speaker อีก ต้องมานัดกี่คนเนี่ย"*

## ⚠️ ความจริงที่ต้องยอมรับ (วิเคราะห์แล้ว)
- **pain point 4 ใน 5 ข้อ justify ได้แค่คำว่า "online" ไม่ได้ justify คำว่า "2D"** — มีเพียงข้อสุดท้ายที่ Zoom แก้ไม่ได้
- **คู่แข่งที่แท้จริงคือ Zoom Webinar + Google Form + LINE OA** ซึ่งรวมกันเกือบฟรี ไม่ใช่งานออนไซต์
- **pain นี้ไม่ได้เจ็บ (vitamin ไม่ใช่ painkiller)** — เหมือน Slack, Notion, Figma, Kahoot ที่โตได้ทั้งที่ไม่ได้แก้ปัญหาที่ถ้าไม่มีแล้วล่ม
- **สิ่งที่ชดเชยความไม่เจ็บได้มี 3 อย่าง**: ความถี่ในการใช้ · distribution · แรงเสียดทานต่ำ
  - ZEP ชนะเพราะครูใช้สัปดาห์ละหลายครั้ง + มีโรงเรียนใช้อยู่แล้ว + คลิกลิงก์เดียวเข้าได้
  - เราแย่กว่าในสองข้อแรก → ชดเชยด้วย **การเลือกลูกค้าที่จัดงานเป็นประจำ** + ยืม distribution จากคณะและคอมมูนิตี้

### ⭐ ข้อสรุปที่ตามมา: โฟกัสงานที่จัดซ้ำ ไม่ใช่งานประจำปี
ลูกค้าที่จัดเดือนละครั้ง = **12 เท่า**ของลูกค้าที่จัดปีละครั้ง ทั้งในแง่รายได้และในแง่ข้อมูลที่เราจะได้เรียนรู้
กลุ่มเป้าหมายที่เข้าข่าย (ในไทย):
- **คอมมูนิตี้เทคที่จัด meetup ประจำ** — เช่น Creatorsgarten และกลุ่มคล้ายกัน (⚠️ ต้องไปเช็ครูปแบบและความถี่จริงเอง)
- **ชมรม/สมาคมวิชาชีพ** ที่มีนัดพบสมาชิกเป็นรอบ
- **หลักสูตร/คณะ** ที่มี guest speaker หรือ seminar ประจำเทอม
- **บริษัทที่มี town hall / brown bag / all-hands รายเดือน**

→ ระบุใน proposal ว่าเป้าหมายคือ **"ผู้จัดงานที่มีกิจกรรมสม่ำเสมอ"** ไม่ใช่ "ผู้จัดงานทั่วไป"

# 9. Business Model

## โมเดล: จองความจุล่วงหน้า (capacity reservation)
**เหตุผล**: ลูกค้าต้องตั้งงบและขออนุมัติล่วงหน้า — ถ้าไม่รู้ราคาก่อน ดีลจบตั้งแต่ยังไม่เริ่ม
**ข้อดีซ่อน**: ได้เงินก่อนวันงาน = กระแสเงินสดดี

```
สร้างงาน → เลือกความจุ → เห็นราคาทันที → จ่าย → ได้ลิงก์

  Starter    ≤ 50 คน   1 วัน
  Standard   ≤150 คน   1 วัน
  Pro        ≤300 คน   1 วัน
  + บูธ sponsor  ___ บูธ
  + เพิ่มวัน     ___ วัน
```

**หลักการ**: ขายความจุ ไม่ได้ขายการใช้งาน (เหมือนจองห้องประชุม 100 ที่นั่ง มาจริง 80 ก็จ่ายเท่าเดิม)
⚠️ คิด flat rate ต่องานไม่ได้ เพราะต้นทุนผันตาม **peak concurrent × ชั่วโมง** (bandwidth ของ SFU)

## Soft cap — เมื่อคนล้นเกิน
- เกินได้ถึง **20%** โดยไม่คิดเงินเพิ่ม
- เกิน 20% → แจ้ง organizer แบบ realtime พร้อมปุ่มอัปเกรด
- ถ้าไม่กด → คนส่วนเกินยังเข้าได้แต่เป็น **โหมดผู้ชม** (ดูเวทีได้ แชทได้ ไม่มีเสียง ไม่มี avatar)
- **เหตุผล**: คนล้นมักเป็นคน "แวะดู" และโหมดผู้ชมกิน bandwidth น้อยกว่ามาก → งานลูกค้าไม่พัง ต้นทุนไม่พุ่ง มีจังหวะ upsell

## รายได้อื่น
- ⭐ **Sponsor booth add-on** ← margin ดีสุด (พร้อม AI assistant + export lead)
- Subscription สำหรับองค์กรที่จัดงานประจำ (เพื่อให้มีรายได้ recurring ถ่วง)
- Usage-based เฉพาะส่วนเสริม: AI booth bot (ตามจำนวนคำถาม) · บันทึกวิดีโอ (ตามชั่วโมง)

## ⚠️ เลื่อนไว้ก่อน
**Paid event / ticketing / payment gateway** — เป็นอีกโปรเจคหนึ่ง (refund, จ่ายเงินคืน organizer, ใบกำกับภาษี) → ให้ link ออกไปเก็บเงินข้างนอก
> ⚠️ อย่าสับสนกับ **"ตั๋ว/เช็คอิน"** ใน feature list — อันนั้นคือ *ตั๋วเพื่อคุมสิทธิ์เข้างาน* (รหัสเชิญ + รายชื่อที่ organizer อัปโหลด ในโหมด INVITE) ไม่เกี่ยวกับการเก็บเงินจากผู้เข้าร่วม

## ประเภทธุรกิจ
**B2B multi-tenant SaaS** แบบ usage-based
- ⚠️ margin ต่ำกว่า SaaS ซอฟต์แวร์ล้วน เพราะ **bandwidth เป็นต้นทุนผันแปรตรงๆ** (หน้าตาใกล้ Zoom/Twilio มากกว่า Notion)
- ⚠️ รายได้ไม่ใช่ recurring แบบคลาสสิก → วัดด้วย **รายได้เฉลี่ยต่องาน · จำนวนงานต่อลูกค้าต่อปี · สัดส่วนลูกค้าที่กลับมาจัดงานที่ 2** ไม่ใช่ MRR/ARR
- ถ้ามีส่วนแบ่งค่าบูธ sponsor จะมีองค์ประกอบของ marketplace แต่ไม่ใช่ marketplace เต็มตัว

## ข้อกำหนดทางเทคนิคที่ตามมา
1. **ตัวนับ concurrent ที่แม่นยำ** (ผูกกับ spike A4 — ghost connection ทำให้ตัวนับเพี้ยนแล้วบล็อกคนจริง)
2. **จุดบังคับ quota ตอนออก LiveKit token** (token คือประตูเดียวที่คุมสิทธิ์ได้จริง)
3. **หน้า monitor สำหรับ organizer ระหว่างงาน** + ปุ่มอัปเกรด (organizer ชอบอยู่แล้วโดยไม่เกี่ยวกับเงิน)
4. **Multi-tenancy ตั้งแต่วันแรก** — ทุกตารางมี `eventId`/`orgId` · ทุก query กรองด้วย tenant (ลืมที่เดียว = ข้อมูลรั่วข้ามลูกค้า)

## ⭐ Carbon Impact Report เป็นฟีเจอร์จริง ไม่ใช่ย่อหน้าใน proposal

- ⚠️ ใช้ emission factor จาก **TGO (องค์การบริหารจัดการก๊าซเรือนกระจก)** หรือ UK DEFRA — **ระบุแหล่งเสมอ ห้ามใช้ตัวเลขที่จำมา**
- ใช้ข้อมูล bandwidth ชุดเดียวกับ spike A8
- **เป็นทั้ง SDG contribution และจุดขายทางธุรกิจ** (บริษัทจดทะเบียนไทยต้องรายงาน ESG อยู่แล้ว)
- ตอน defense ตอบได้ว่า "ระบบคำนวณและรายงานตัวเลขนี้ให้ทุกงาน นี่คือหน้าจอครับ" ไม่ใช่ "ช่วยลดโลกร้อนครับ"

## ข้อจำกัดที่ควรเขียนเอง (เพิ่มความน่าเชื่อถือ)
- ดิจิทัลไม่ได้ปล่อยศูนย์ — server, bandwidth, อุปกรณ์ผู้ใช้ใช้พลังงาน → เป็น "ลดลงอย่างมีนัยสำคัญ" ไม่ใช่ "เป็นศูนย์"
- **Rebound effect** — จัดงานถูกลง = จัดถี่ขึ้น ทำให้ผลสุทธิลดลงกว่าที่คำนวณ (เป็นข้อถกเถียงจริงในงานวิจัย digital sustainability)

| Realtime | **Colyseus** (Node) | room lifecycle + delta state sync + schema + client SDK สำเร็จรูป |
| API | **NestJS** | โครงสร้างบังคับ เหมาะทีมหลายคน · guard เป็นที่ทางของ permission |
| Media | **LiveKit** (self-host Docker) | SFU + TURN/TLS + egress ในตัวเดียว · **เขียนแต่ JS ไม่ต้องเขียน Go** |
| DB | **PostgreSQL + Prisma** | ต้องการ transaction/row lock สำหรับระบบคิว + pgvector สำหรับ RAG |
| Cache | **Redis** | ตอน MVP ยังไม่ใช้จริง แต่วาง interface ไว้ |
| Auth | **OAuth (Google/Microsoft) + magic link · JWT** | ⭐ ตัดสินใจแล้วว่า **บังคับ login ทุกคน ไม่มี guest join** — ลดความซับซ้อนของ permission ลงครึ่งหนึ่ง และทำให้ ban/lead/analytics ใช้งานได้จริง |
| AI | LLM API + pgvector | booth bot (RAG) + matchmaking |
| Infra | **Docker Compose + Caddy บน VM ของมหาวิทยาลัย** | ฟรี · ไม่มีบิลเซอร์ไพรส์ · ⚠️ ต้องเช็ค UDP port range + public IP ก่อน (ดูหัวข้อ 12) |

## เหตุผลรายตัวแบบเต็ม (สำหรับตอบ defense)

### ทำไม Node ไม่ใช่ Go (ตัดเรื่องความถนัดออกแล้ว)
1. **bottleneck ของระบบนี้คือ bandwidth ไม่ใช่ CPU** → ข้อดีของ Go (multi-core, GC latency ต่ำ, memory เล็ก) ไม่ถูกใช้เลย ที่ 30–80 คน ส่ง position 10–15Hz payload ไม่กี่สิบไบต์ ห่างจากขีดจำกัดของ Node มาก → เลือก Go ที่นี่ = premature optimization
2. **Colyseus ไม่มีของเทียบเท่าใน Go** → เลือก Go = ต้องเขียน delta encoding + schema sync + client SDK เอง ~3–4 สัปดาห์ที่ไม่ทำให้ product ดีขึ้น
3. **type ร่วมระหว่าง client/server** มีค่ามากในระบบที่มี message หลายสิบแบบ — Go ให้ไม่ได้
4. **ภาษาเดียวถูกกว่าสองภาษาเสมอ** ถ้าไม่มีเหตุผลชดเชย (toolchain/CI/Docker 2 ชุด, schema เขียนซ้ำ 2 ที่)

**เงื่อนไขที่จะพลิกเป็น Go**: ห้องเดียวหลักพันคน · tick 30–60Hz · มี physics/pathfinding หนัก · ต้องการ sub-ms latency — **ไม่ผ่านสักข้อ**

### ทำไม NestJS ไม่ใช่ Express/Fastify
เหตุผลเดียว: **ทีม 3 คนเขียนพร้อมกัน** — ซื้อ "การไม่ต้องถกเถียง" ว่าวางไฟล์ยังไง validate ที่ไหน auth check ตรงไหน
- **Guard** = ที่ทางที่ชัดเจนของ permission (event role 5 แบบ ที่ 1 คนมีได้หลาย role + app role + multi-tenant + เจ้าของงาน + quota) — ถ้าใช้ Express จะกระจายเป็น `if` แล้ววันหนึ่งจะมีคนลืมเช็คที่ endpoint เดียว = ข้อมูลรั่ว
- **DTO + ValidationPipe** บังคับให้ทุก endpoint ประกาศว่ารับอะไร
- **Module boundary** มองเห็นได้ → แบ่งงาน 3 คนง่าย และเห็นรอยตัดถ้าจะแยกเป็น service ทีหลัง
- **DI ทำให้เทสได้** → สำคัญตอน spike C2 (ยิง 20 request พร้อมกันโดยไม่ต้องแตะ LiveKit จริง)
- ⚠️ ยอมรับ: boilerplate เยอะ + learning curve DI ~1 สัปดาห์ (ต้องนับไว้ในแผน)

#### ทำไมไม่ใช้ Java Spring Boot (ทั้งที่มีคนในทีมถนัด)
1. ⭐ **Colyseus เป็น Node ไม่ว่าจะเลือกอะไร** → เลือก Java = **ภาษาที่สอง ไม่ใช่ภาษาแรก** (2 toolchain, 2 Docker build, 2 CI, schema เขียนซ้ำ 2 ที่) — เหตุผลเดียวกับที่ตัด Go แต่หนักกว่าเพราะ JVM กิน RAM ~300–500MB เทียบกับ Node ~60MB บน VM ที่รัน 6 container
2. **NestJS ถูกออกแบบตาม Spring** — `@RestController`→`@Controller` · `@Service`→`@Injectable` · Spring Security filter→`Guard` · `@Valid`→`ValidationPipe` · `@Configuration`→`@Module` · คนเขียน Spring เป็นขึ้น NestJS ได้ **3–5 วัน** สิ่งที่ต้องเรียนใหม่จริงคือ TypeScript + Prisma ไม่ใช่ architecture
3. **bus factor** — ถ้าเขียน Java คนเดียว อีก 2 คนแตะชั้น API ไม่ได้ตลอดปี
4. ⚠️ LiveKit ไม่มี server SDK สำหรับ Java อย่างเป็นทางการ (**ต้องเช็ค livekit.io/docs เองก่อนอ้างอิง**) → อาจต้องเขียน JWT เอง

**สิ่งที่ทำแทน**: ให้คนที่ถนัด Spring เป็นคนนำการออกแบบชั้น API — pattern ที่เขารู้ (module boundary, service layer, transaction, exception handling) มีค่ากว่า syntax ที่เรียนใหม่ไม่กี่วัน

### ทำไม Next ไม่ใช่ React + Vite
> ⚠️ **เปลี่ยนจากข้อสรุปเดิม (1 ก.ย. 2026)** — ข้อสรุปเดิมคือ Vite ด้วยเหตุผลว่า Phaser ต้องการ `window` ตั้งแต่ initialize ซึ่งไม่มีบน server ตอน SSR
> **เหตุผลที่เปลี่ยน**: ทีมถนัด Next อยู่แล้ว — ปัจจัยความถนัดมีน้ำหนักมากกว่าที่ประเมินไว้ตอนแรก สำหรับทีม 3 คนที่มีเดดไลน์ 1 ปี

**⭐ เหตุผลสำหรับตอบ defense** (ห้ามตอบว่า "ทีมถนัด" หรือ "เทคใหม่")
1. **ระบบมีทั้งส่วน public และส่วนหลัง login** — landing และหน้าเชิญงาน `/event/[id]` ต้องการ SSR + **Open Graph card** เพราะลิงก์เชิญถูกแชร์ผ่าน LINE/Facebook ซึ่งเป็นช่องทาง distribution หลักของกลุ่มเป้าหมาย (หัวข้อ 6 — เราชดเชย distribution ด้วยการยืมจากคณะและคอมมู)
2. **ไม่ต้อง maintain 2 codebase** — ข้อสรุปเดิมยอมรับอยู่แล้วว่าต้องมี Next แยกสำหรับหน้า marketing อยู่ดี → ใช้ Next ตัวเดียวถูกกว่า
3. **route group แยกสองโลกได้ในโปรเจคเดียว** — `app/(marketing)/` เป็น Server Component ได้ SEO · `app/(app)/` เป็น client-only สำหรับโลก 2D
4. **ทีมวิ่งได้วันแรก** — สำหรับ capstone 1 ปี เวลาเรียนของใหม่มีต้นทุนจริง

**ราคาที่ต้องจ่าย — พิสูจน์จริงจาก spike B1 แล้ว (เขียนลง feasibility ได้)**
- Phaser ต้องโหลดผ่าน `dynamic(..., { ssr: false })` เสมอ
- ⚠️ **Next 15.5+ ห้ามใช้ `ssr:false` ใน Server Component** → ต้องมี client wrapper คั่น (`"use client"` + dynamic import) — เป็น pattern ประจำของทุก Phaser component
- Phaser 3.90 ไม่มี default export → `import * as Phaser from "phaser"`
- ต้อง `destroy()` Phaser instance ใน cleanup ของ `useEffect` ไม่งั้น fast-refresh leak
- hydration mismatch เวลาอ่าน `localStorage`/`window` ตอน first render → ใช้ `useEffect` + mounted flag
- HMR ช้ากว่า Vite เมื่อ Phaser scene ใหญ่ขึ้น

→ ตัวอย่างโค้ดทั้งหมดอยู่ที่ `reference/nextjs-starter` และ `b1-phaser-tilemap` ใน repo POC
→ `reference/react-starter` เก็บไว้เป็น **หลักฐานว่าเปรียบเทียบแล้วจริง** ไม่ใช่เดา

### ทำไม LiveKit ไม่ใช่ mediasoup / mesh / เขียนเอง
- **mesh พังที่ ~6 คน** = ต่ำกว่างานที่เล็กที่สุดที่ขายได้
- **mediasoup** เป็น Node ก็จริง แต่เป็น library ระดับล่างที่ต้องประกอบ room logic + permission + **TURN แยกเอง**
- **LiveKit มี TURN/TLS ในตัว** ตัดงานไปหลายสัปดาห์
- **เขียน SFU เอง** = RTP/SRTP, DTLS, ICE, congestion control (TWCC/REMB), packet loss recovery (NACK/RTX/FEC), jitter buffer, simulcast → หลาย person-year

### ทำไม PostgreSQL ไม่ใช่ MongoDB
- ข้อมูล relational ชัดเจน (event → session → speaker → คิว → ผู้จอง)
- **ระบบคิว 1:1 ต้องการ transaction จริง + row-level lock** เพื่อกัน double-booking
- **pgvector** ทำ RAG ได้ในฐานข้อมูลเดียวกัน ไม่ต้องมี vector DB แยก

### ทำไม 2D ไม่ใช่ 3D
ต้นทุนผลิตเนื้อหาต่ำ · ทุกวัยใช้เป็นโดยไม่ต้องเรียนรู้ · ไม่ต้องติดตั้ง · เครื่องสเปคต่ำเล่นได้ · **คุณค่าหลักคือ spatial presence ซึ่ง 2D ให้ได้ครบแล้ว**
— **ไม่ใช่เพราะทำ 3D ไม่ได้** (ดูบทเรียน ZEP ข้อ 13)

## จงใจไม่ใช้ (ตารางนี้มีค่าพอๆ กับตารางบน)
| ไม่ใช้ | เหตุผล |
|---|---|
| Kubernetes | service 5 ตัวบนเครื่องเดียว ได้แต่ความซับซ้อน |
| Microservices เต็มรูป | 3 process ที่แยกด้วยเหตุผลชัดเจนพอแล้ว |
| Vector DB แยก | pgvector พอสำหรับเอกสารระดับบูธ |
| Kafka / RabbitMQ | ไม่มี event volume ที่ต้องใช้ |
| GraphQL | client มีตัวเดียว ไม่มีปัญหา over-fetching |
| WebRTC mesh | พังที่ 6 คน |

## กฎการวางโค้ด
- **แบ่งหน้าที่ตามอายุของข้อมูล**: Colyseus ถือ state ที่มีอายุเท่า session (ตำแหน่ง, ใครอยู่ในห้อง, ใครกำลังพูด, สถานะคิว) · NestJS ถือข้อมูลถาวร (event, user, ตั๋ว, booth, สรุปหลังงาน)
- ห้าม Colyseus เขียน DB ทุก tick → persist เป็นช่วงๆ หรือตอนจบ session
- 🔒 **LiveKit token ต้องออกจาก NestJS เท่านั้น** — ถ้าออกจาก client ใครก็ปลอมเป็น speaker ได้
- 🔒 **`roomId`/`eventId` อยู่ในทุก state key และทุก method signature ตั้งแต่วันแรก**
- shared state วิ่งผ่าน interface เดียว (วันนี้เป็น `Map` วันหน้าเปลี่ยนเป็น Redis แก้ที่เดียว)

```ts
interface PresenceStore {
  setPosition(roomId: string, userId: string, pos: Vec2): Promise<void>
  getNearby(roomId: string, pos: Vec2, radius: number): Promise<string[]>
  remove(roomId: string, userId: string): Promise<void>
}
```

**หลักการรวม**: *ไม่สร้างเผื่อ แต่ไม่ปิดประตูตัวเองฟรีๆ*
- capacity = ประตูสองทาง (เลื่อนได้ เพิ่ม server ทีหลังได้)
- shape ของ data = ประตูทางเดียว (แก้ทีหลังแพงมาก)
- การใส่ `roomId` ตั้งแต่แรกใช้เวลาเพิ่ม 0 นาที แต่ประหยัดการรื้อเป็นสัปดาห์

# 12. สถาปัตยกรรมและ Deployment

## Container (7 ตัว)
```
Browser
 ├─ TCP 443 ──→ Caddy (TLS) ──┬──→ api        (NestJS  :3000)
 │                             ├──→ realtime   (Colyseus :2567)
 │                             └──→ livekit    (signaling :7880)
 └─ UDP 50000-60000 ─────────────→ livekit    (media ตรง ไม่ผ่าน Caddy)
    (fallback: TCP/TLS 443 ผ่าน TURN)

api      → postgres :5432, redis :6379, livekit :7880 (สร้าง/ปิด room), minio :9000
realtime → postgres :5432, redis :6379
```

⚠️ **เพิ่ม MinIO (S3-compatible) เป็น container ที่ 7** — จำเป็นตั้งแต่มีฟีเจอร์บูธ เพราะ exhibitor อัปโหลด PDF/สไลด์/รูป **ห้ามเก็บไฟล์ใน Postgres** และห้าม serve จาก public bucket (ใช้ signed URL ที่หมดอายุ) · ต้องตรวจ MIME type จริงฝั่ง server ไม่เชื่อนามสกุลไฟล์

⭐ **จุดสำคัญที่สุด**: media เป็น UDP และ throughput สูงเกินกว่าจะผ่าน reverse proxy → **browser ต่อ LiveKit ตรง** ข้อนี้กำหนดทุกอย่างในการเลือก infra

## 🖥️ Deployment: VM ของมหาวิทยาลัย (ตัดสินใจแล้ว — ไม่ใช้ AWS)

มหาวิทยาลัยเตรียม VM ไว้ให้ → ใช้ **Docker Compose ทั้ง 6 container บน VM** ตามผังด้านบน
**ข้อดี**: ฟรี · ไม่มีบิลเซอร์ไพรส์ · ไม่ต้องเสียเวลากับ VPC/IAM/NAT Gateway · ตรงกับสถาปัตยกรรมที่ออกแบบไว้อยู่แล้ว

### 🔴 spike C0 — ตรวจสอบความสามารถของ VM (ทำก่อนทุกอย่าง)
VM ของมหาวิทยาลัยมีข้อจำกัดที่ VPS เชิงพาณิชย์ไม่มี และ **lead time ของฝ่าย IT มักเป็นสัปดาห์** → ถามตั้งแต่วันแรก ไม่ใช่ตอนจะ deploy

#### คำถามที่เป็น go / no-go
| # | คำถาม | ทำไมถึงสำคัญ | ถ้าคำตอบเป็น "ไม่" |
|---|---|---|---|
| 1 | **VM มี public IP ที่เข้าถึงจากนอกเครือข่ายมหาลัยได้ไหม** | ผู้เข้าร่วมงานส่วนใหญ่อยู่นอกมหาลัย ถ้าเข้าไม่ได้คือไม่มี product | 🔴 ต้องหา VPS ข้างนอกมาเป็นทางเข้าหลัก |
| 2 | **เปิด UDP port range 50000–60000 inbound จาก internet ได้ไหม** | LiveKit ส่ง media ผ่าน UDP หลายพอร์ตพร้อมกัน — เปิดทีละพอร์ตไม่ได้ · **เครือข่ายมหาวิทยาลัยแทบทุกที่บล็อก UDP range กว้างเป็นค่าเริ่มต้น** | 🔴 LiveKit self-host ใช้ไม่ได้ → แยก media ออกไปข้างนอก |
| 3 | **ชี้ domain (หรือ subdomain ของคณะ) มาที่ VM และออก TLS cert จริงได้ไหม** | TURN over TLS ต้องมี cert จริง ถ้าไม่มี = คนที่อยู่บนเน็ตที่บล็อก UDP เข้าไม่ได้เลย | 🔴 ต้องซื้อ domain เอง หรือใช้ DNS-01 challenge |

#### คำถามที่กระทบขนาดงานและความเสี่ยง
| # | คำถาม | ทำไมถึงสำคัญ |
|---|---|---|
| 4 | เปิด TCP 80/443 inbound ได้ไหม | Caddy ออก cert อัตโนมัติด้วย HTTP-01 ต้องใช้ 80 — ถ้าปิด ต้องเปลี่ยนไป DNS-01 |
| 5 | มีเพดาน bandwidth / traffic shaping / QoS ไหม | กระทบทั้ง load test (A7) และงานจริง — media กิน egress สูง |
| 6 | spec เท่าไหร่ (vCPU / RAM / disk) | ต้องการอย่างน้อย ~4 vCPU / 8 GB สำหรับ 6 container ที่ 30–80 คน |
| 7 | มี reverse proxy / WAF ของมหาลัยคั่นอยู่ไหม | ถ้ามี ต้องเช็คว่ารองรับ **WebSocket upgrade** (Colyseus ต้องใช้) และไม่ตัด connection ที่ค้างนาน |
| 8 | ใครดูแล firewall · lead time การขอเปิดพอร์ตกี่วัน | ตัวกำหนดว่าจะเริ่ม A0 ได้เมื่อไหร่ |
| 9 | maintenance window / นโยบายปิดช่วงปิดเทอม | ห้ามชนวัน defense |
| 10 | เก็บข้อมูลผู้ใช้ภายนอกบน infra มหาลัยได้ไหม (เชิงนโยบาย) | ถ้าเปิดให้คนนอกลงทะเบียน อาจติดระเบียบ |
| 11 | VM อยู่ถึงเมื่อไหร่ · backup ใครดูแล | ต้องรู้ก่อนวางแผนเก็บข้อมูลระยะยาว |

#### ⭐ ลำดับที่ถูกต้อง: ทดสอบเองก่อน แล้วค่อยถาม
ข้อ 1–5 ส่วนใหญ่**ทดสอบเองได้ภายในครึ่งวัน**ถ้ามีสิทธิ์ ssh เข้า VM — อย่ารอ IT ในสิ่งที่ตอบเองได้
รายละเอียดคำสั่งทดสอบและข้อความสำหรับถามอาจารย์อยู่ในไฟล์ `vm-questions-for-advisor.md`

สรุปวิธีทดสอบเอง:
- **มี public IP จริงไหม** → เทียบ `ip -4 addr` กับ `curl -4 ifconfig.me` · ตรงกัน = public IP โดยตรง ✅ · ไม่ตรง = อยู่หลัง NAT ต้องตั้ง LiveKit ให้ประกาศ IP ภายนอก
- **UDP ทะลุไหม** ⭐ → เปิด UDP listener ที่ 50000/55000/60000 บน VM แล้วยิง `nc -u` จาก**มือถือที่ต่อ 4G** (ห้ามใช้ wifi มหาลัย เพราะอยู่ในวงเดียวกันจะทะลุหลอกๆ)
- **80/443 ใช้ได้ไหม** → `sudo python3 -m http.server 80` แล้วเปิดจากข้างนอก
- **spec / sudo / docker** → `nproc`, `free -h`, `sudo -v`, `docker --version`

⚠️ `iptables`/`ufw` บนเครื่องบอกได้แค่ firewall ระดับเครื่อง — **firewall ขอบเครือข่ายของมหาวิทยาลัยเป็นคนละชั้น** ต้องทดสอบจากนอกเครือข่ายจริงเท่านั้น

**การทดสอบที่ตรงที่สุด**: รัน LiveKit จริงบน VM แล้วลองเข้าจากมือถือ 4G — ถ้าได้ยินเสียง = ผ่านทุกข้อในคราวเดียว

### 🖥️ ระหว่างยังไม่ได้ VM — พัฒนาบน localhost ไปก่อนได้เลย
**ห้ามรอ VM** งานเกือบทั้งหมดทำบน localhost ได้:

| ทำบน localhost ได้ | ทำไม่ได้ / ได้ผลหลอก |
|---|---|
| A0 LiveKit hello-world · A1 movement sync · A2 logic ของ proximity (รัศมี, hysteresis, subscribe/unsubscribe, falloff) | ⚠️ **A3 ทั้งหมด** — localhost ไม่มี NAT ไม่มี ICE ไม่ต้องใช้ TURN → **ผ่านฉลุยเสมอ ซึ่งเป็นความมั่นใจหลอก** |
| B1–B4 ทั้งหมด (Phaser, Tiled, React integration) | ⚠️ A2 ในแง่คุณภาพจริง — ไม่มีไมค์จริงหลายตัว ไม่มี echo ไม่มี network jitter |

### ข้อควรระวังตอน deploy
- ⚠️ **LiveKit ต้องการ UDP port range กว้าง — เปิดที่ firewall ของผู้ให้บริการ/มหาลัยด้วย ไม่ใช่แค่ที่ OS**

- ถ้ามี reverse proxy ของมหาลัยคั่นอยู่ ต้องเช็คว่ารองรับ **WebSocket upgrade** ไหม (Colyseus ต้องใช้)

### ประโยคสำหรับ proposal
> ระบบพัฒนาแบบ containerized ทุก service เพื่อให้ deploy ได้ทั้งบนเครื่องเดียวและย้ายขึ้น cloud ได้โดยไม่ต้องแก้โค้ด โดยใช้ Docker Compose บนเครื่องแม่ข่ายของมหาวิทยาลัย ซึ่งเหมาะกับรูปแบบการใช้งานที่เป็นช่วง (event-based) และมีต้นทุนคงที่ต่ำ ทั้งนี้ได้ออกแบบให้ส่วน media server สามารถแยกไปยังเครื่องอื่นได้ เนื่องจากมีลักษณะการใช้ทรัพยากรที่ต่างจากส่วนแอปพลิเคชัน

**หมายเหตุสำหรับตอบ defense**: ถ้าถูกถามว่าทำไมไม่ใช้ cloud — ตอบว่าประเมินแล้วว่า managed service (ALB/NLB) **ไม่รองรับ UDP port range ที่ WebRTC ต้องใช้** ทำให้ media server ต้องอยู่บนเครื่องที่รับ traffic ตรงจาก internet อยู่ดี จึงไม่ได้ประโยชน์จาก cloud มากพอที่จะคุ้มค่าใช้จ่ายและความซับซ้อน

# 13. ความรู้ WebRTC ที่ต้องไม่ลืม

## ทำไมต้องมี SFU
- **Mesh**: คนที่ n ต้องอัปโหลด n−1 ชุด → พังที่ ~6 คน (upload ในไทยมักน้อยกว่า download)
- ⭐ **ปัญหาที่ร้ายกว่า**: proximity ต้องสร้าง/ทิ้ง connection ตลอดเวลาที่คนเดิน แต่ละครั้งกิน ICE gathering + DTLS handshake + SRTP key exchange หลักร้อย ms ถึงวินาที → **เสียงขาดทุกครั้งที่เดินผ่านใคร**
- **SFU**: อัปโหลดชุดเดียว ท่อขึ้น server ไม่ต้องรื้อ เปลี่ยนแค่ subscription เร็วระดับ ms
- ⭐ **logic ทั้งหมดของ proximity audio = การเปลี่ยน subscription list ตามระยะห่างของ avatar** (โค้ดไม่กี่สิบบรรทัด)

## ทำไมต้องมี TURN
- **ICE ไล่ลำดับ**: host candidate (LAN เดียวกัน) → **STUN** (บอก public IP เพื่อเจาะ NAT, เวิร์ค ~70–85%) → **TURN** (relay ทุก byte ผ่าน server, ช้ากว่า แพงกว่า แต่ไม่มีทางต่อไม่ติด)
- **กรณีที่ STUN พังแน่ๆ**: symmetric NAT · **CGNAT (ค่ายมือถือไทยแทบทุกเจ้า)** · **เน็ตองค์กร/มหาลัยที่บล็อก UDP** · VPN บางตัว
- ⚠️ **วันพรีเซนต์อยู่บนเน็ตมหาลัย = สภาพแวดล้อมแย่ที่สุด** — ถ้าไม่มี TURN over TLS 443 อาการคือ **"เข้าห้องได้ เห็น avatar เดินได้ แต่ไม่ได้ยินเสียง"** ซึ่งดูเหมือนบั๊กของเรา
- ⚠️ **SFU ไม่ได้แทน TURN** — SFU แก้ปัญหา*จำนวนคน* TURN แก้ปัญหา*เข้าถึงไม่ได้* (client ยังต้องยิง UDP ไปหา SFU อยู่ดี)
- ✅ LiveKit มี TURN/TLS ในตัว → ตั้ง domain + cert (Caddy จัดการให้) แล้วจบ

## ICE/NAT ต้องเรียนแค่ไหน
**เรียนตอนเจอปัญหาจริง ~2–3 ชม.** ตอบ 5 คำถามนี้ได้พอ:
1. host / srflx / relay candidate ต่างกันยังไง
2. STUN กับ TURN ต่างกันตรงไหน
3. ทำไม symmetric NAT ทำให้ hole punching ล้มเหลว
4. ทำไม TURN over TCP 443 ผ่าน firewall องค์กรได้
5. ดู candidate pair ที่ถูกเลือกใน `chrome://webrtc-internals` ตรงไหน

**ไม่ต้องรู้**: RFC, STUN message format, ICE priority formula, การเขียน ICE agent

⭐ **เรียน `chrome://webrtc-internals` ตั้งแต่สัปดาห์แรก ก่อนเขียน feature ด้วยซ้ำ** — บั๊กกลุ่มนี้ **ไม่มี error message** (connected ✅ track subscribed ✅ แต่เงียบ 🔇) คนที่อ่านหน้านี้เป็นกับไม่เป็น ใช้เวลาแก้บั๊กเดียวกันต่างกัน 10 เท่า

## ค่าที่ต้องหาจาก spike (จะกลายเป็น config ของ product)
- **tick rate**: เริ่ม 10Hz ไล่ขึ้น (10–15Hz พอ)
- **hysteresis ของ proximity**: ⚠️ subscribe ที่รัศมี ~8 ช่อง แต่ unsubscribe ที่ ~12 ช่อง — **ห้ามใช้ตัวเลขเดียวกัน ไม่งั้นคนยืนขอบรัศมีจะ toggle รัวๆ**
- **falloff**: คูณ gain เฉยๆ หรือใช้ Web Audio `PannerNode` (ได้เสียงซ้าย-ขวา)
- **เพดาน audio track ต่อ browser**: คาดว่า 20–30
- **relay ratio**: ปกติ 10–30% (เกิน 50% = config ผิด) ← ตัวคูณต้นทุน bandwidth
- **bitrate**: เสียง ~40 kbps/คน · วิดีโอ speaker ~1.5 Mbps

- **A6**: ✅ `roomId` ในทุก key · ✅ shared state ผ่าน interface เดียว · ✅ ไม่มี global mutable state · ✅ DB schema มี event เป็น first-class → บันทึกว่า "ถ้าเปลี่ยนเป็น Redis ต้องแก้ที่ไหน กี่วัน" (ใช้ตอบ defense)
- **A7**: **อะไรพังก่อน** — CPU/RAM/bandwidth/จำนวน WebSocket · เพดานต่อ 1 VPS กี่คน · ใกล้เพดานอาการเป็นยังไง
- **B2 เกณฑ์ผ่านที่ดีที่สุด**: คนในทีมที่**ไม่เขียนโค้ด**ทำแมปใหม่ได้ใน 2 ชั่วโมง
- **B3**: Phaser คุม canvas / React คุม UI — สื่อสารกันยังไง · state ไหนอยู่ที่ไหน · hot reload พังไหม (Phaser มัก leak instance)
- **C1**: OAuth flow ครบไหม · 1 คนมีหลาย role ในงานเดียว สิทธิ์ union ถูกไหม · assign role ระหว่างงานแล้ว UI อัปเดตทันทีไหม · staff งาน A แตะงาน B ได้ไหม (ต้องไม่ได้) · role check ต้องอยู่ที่ server ทุกจุด (REST + WebSocket message + LiveKit token grant) · **ทดสอบด้วยการพยายามโกง 5 แบบ**
- **C2**: 20 คนกดจองช่องเดียวกันพร้อมกัน → ต้องได้คนเดียว (row lock/optimistic) · timer ต้องเป็น **server-side** (เตะออกแม้ปิด tab) · คนในคิวหลุดเน็ตถือว่าสละสิทธิ์หรือรอ
- **C4**: ⚠️ **LiveKit ต้องการ UDP port range กว้าง — เปิดที่ firewall ของผู้ให้บริการด้วย ไม่ใช่แค่ OS** · TURN over TLS ต้องมี domain + cert จริง

## Go / No-Go สิ้นสัปดาห์ที่ 4
| สถานะ | ทำอะไร |
|---|---|
| A2 ทำงานกับคนจริง 5+ คน | ✅ เดินหน้าตามแผน |
| ทำงานแต่ไม่เสถียร | ⚠️ ให้เวลาเพิ่ม 1 สัปดาห์ |
| ยังไม่ทำงานเลย | 🔴 **ไต่บันไดแผนสำรองในหัวข้อ 15** |
| A0 ยังไม่ผ่าน | 🔴 ประชุมทบทวนทั้งหมด |

⭐ **การใช้แผนสำรองไม่ใช่ความล้มเหลว — การดันต่อจนหมดเวลาต่างหากที่ใช่**

## ธงแดง
- spike ไหนเกิน timebox **2 เท่า** → หยุด ประชุม ตัดสินใจใหม่
- เริ่มเขียน UI สวยๆ ตอน spike → หลงทาง
- เอาโค้ด spike ไปต่อยอด production → ผิดหลักการ ทิ้งแล้วเขียนใหม่

# 15. บันไดแผนสำรองด้านเสียง

**หลักการของทีม**: สิ่งที่ต้องรักษาไว้คือ **core technology (Phaser + 2D multi-user world)** ถ้า voice/video ไม่เวิร์คจริงๆ การหา business model ใหม่ไม่ใช่เรื่องยาก

**แต่ก่อนจะไปถึงตรงนั้น มีขั้นกลางที่ถูกกว่า** — เปลี่ยน "ชั้นปฏิสัมพันธ์" แทนที่จะเปลี่ยนทั้งโมเดล
เพราะการเปลี่ยนโมเดลธุรกิจ = เขียนใหม่ทั้ง proposal, STP, competitive analysis, SDG, pricing
ส่วนการเปลี่ยนชั้นปฏิสัมพันธ์ = **ทุกอย่างรอด** (pain point, STP, SDG 13, carbon report, ระบบคิว 1:1, sponsor booth, capacity pricing)

→ ไต่บันไดลงทีละขั้น ถ้าลงถึงขั้นสุดท้ายแล้วยังไม่พอ ค่อยเปลี่ยน business model

## ⭐ ข้อเท็จจริงที่เปลี่ยนทุกอย่าง
**ระบบคิว 1:1 = คน 2 คนในห้อง = เคส WebRTC ที่ง่ายที่สุดที่มี**
mesh 2 คนทำงานได้ ไม่ต้องมี SFU ไม่ต้องมี proximity logic
→ **ต่อให้ proximity audio ล้มเหลวสิ้นเชิง ก็ยังส่งฟีเจอร์เรือธงได้ครบ**

## บันได 4 ขั้น

| ขั้น | ได้อะไร | ความยาก | ตัดสินใจเมื่อ |
|---|---|---|---|
| **0 (เป้าหมาย)** | proximity audio เต็มรูป (falloff + hysteresis + subscription switching) | 🔴🔴 | — |
| **1** | **โซนเสียง** — เดินเข้าโซน = เข้าห้องเสียงของโซนนั้น (ไม่มี falloff ไม่มี hysteresis คล้าย Zoom breakout ที่ย้ายเองได้) | 🔴 | สิ้นสัปดาห์ 4 |
| **2** ⭐ | **เสียงเฉพาะห้อง 1:1 + เวที** — ตัด proximity ทิ้งทั้งหมด แต่ยังได้ฟีเจอร์เรือธงและ session หลัก | 🟡 | สิ้นสัปดาห์ 6 |
| **3** | **ไม่มีเสียงเลย** — text + quiz + ภารกิจ + stamp rally · คิว 1:1 กลายเป็นห้องแชทส่วนตัวที่มีคิวและ timer | 🟢 | ⚠️ **ไม่เกินเดือนที่ 6** |

**ขั้น 2 คือแผนสำรองที่ดีที่สุด** — ได้ทั้งเสียงและฟีเจอร์เรือธง โดยตัดส่วนที่ยากที่สุด (proximity) ทิ้ง

⚠️ **ขั้น 3 ต้องตัดสินใจไม่เกินเดือนที่ 6** เพราะระบบ quiz/ภารกิจใช้เวลาสร้าง 6–8 สัปดาห์ ถ้าตัดสินใจเดือนที่ 9 จะไม่ทัน

⚠️ **แผนสำรองต้องไม่กลายเป็นข้ออ้างที่จะไม่ลอง** — ยังต้องทำ spike A0/A2 ให้เต็มที่ตาม timebox ก่อนไต่ลงบันได

## ⚠️ หมายเหตุเรื่องลำดับการพัฒนา
เนื่องจากขั้น 3 ไม่ต้องใช้ WebRTC เลย และขั้น 2 ใช้แค่เคสง่ายที่สุด **การเริ่มพัฒนาจากส่วนที่ไม่ต้องใช้เสียงก่อน (โลก 2D + เดิน + แชท + ระบบงาน + คิว) แล้วค่อยเติมเสียงทีหลัง** ทำให้มีของที่ส่งได้แน่นอนตั้งแต่เนิ่นๆ ไม่ว่า WebRTC จะออกมายังไง
(timeline จริงอ้างอิงจากเอกสารของคณะ)

## ถ้าลงไปถึงขั้น 3 — สิ่งที่ต้องเปลี่ยนใน proposal
- ❌ ไม่ต้องเปลี่ยน: ชื่อโปรเจค · pain point · STP · SDG · business model · competitive positioning
- ✅ เปลี่ยนแค่: หัวข้อ feature (เอา voice/video ออก เพิ่ม quiz/ภารกิจ) และประโยคที่เคลมเรื่อง proximity audio
- ✅ เพิ่มในหัวข้อ feasibility study: อธิบายว่าทดสอบ WebRTC แล้วพบข้อจำกัดอะไร (ตัวเลขจาก spike) จึงเลือกออกแบบปฏิสัมพันธ์อีกแบบ — **นี่คือเนื้อหาที่ดี ไม่ใช่ข้อเสีย** เพราะแสดงว่าตัดสินใจบนข้อมูล

# 17. บริบทของรุ่นและการนำเสนอ

## ⭐ สิ่งที่จะทำให้ต่างจากทีมอื่น
จาก 37 ทีม capstone ในรุ่น **มีไม่ถึง 5 ทีมที่จะมีตัวเลขจริงจากการทดสอบไปโชว์** — ส่วนใหญ่โชว์แค่หน้าจอ
→ **spike A7 (load test) + A8 (bandwidth→ต้นทุน) คือความต่างที่แท้จริง มากกว่าความยากของหัวข้อเสียอีก**

**บริบทของรุ่น**: หัวข้อของเราอยู่ใน Tier S (ความเสี่ยงทางเทคนิคสูงสุด ~4 ทีมจาก 37) และเป็นทีมเดียวใน Tier S ที่ต้องทำ **3 โดเมนใหม่พร้อมกัน** (realtime sync + media + game rendering) ส่วนอีก 3 ทีมมีจุดยากจุดเดียว
→ ไม่ได้ยากกว่า แต่ **จำนวนจุดที่พังได้มีมากกว่า** = เหตุผลของการแบ่ง 3 track + แผนสำรอง

**ทับซ้อนกับทีมอื่นในรุ่น** (เตรียมตอบ): Event Calendar and Planning System · ระบบจัดการเข้าชม/ประเมินโครงงานปี 4 · ระบบนำเสนอแบบโต้ตอบ มจธ. · ระบบจัดการแข่งขัน AoV
→ ตอบว่า *"ทีมอื่นทำระบบบริหารจัดการงาน ของเราทำตัวสถานที่จัดงาน เป็นส่วนเสริมกันมากกว่าแข่งกัน"*

**ทีมที่ควรไปคุยแลกความรู้**: ทีมประมูลการ์ดเรียลไทม์ (concurrency, race condition, server timer — ปัญหาเดียวกับระบบคิว) · ทีม guardrail/microservices (สถาปัตยกรรม)

## คำถามที่ต้องเตรียมคำตอบ
| คำถาม | คำตอบ |
|---|---|
| "ทำไมไม่ใช้ Gather" | Gather ถอยไปทำ virtual HQ · SpatialChat/Remo ยังอยู่แต่ไม่มีระบบคิว 1:1 และไม่ทำตลาดไทย |
| "ทำไมไม่ใช้ Zoom" | หลายบทสนทนาพร้อมกันในบริบทเดียว + ระบบคิว 1:1 |
| "ถ้ามีคนใช้ 1,000 คนล่ะ" | "ออกแบบสำหรับ 30–80 คน ทดสอบด้วย bot เจอเพดานที่ X คน คอขวดคือ Y แยก state layer ไว้แล้ว ประเมินว่าเปลี่ยนเป็น Redis ใช้เวลา ~1 สัปดาห์" |
| "ทำไม 2D ไม่ใช่ 3D" | ต้นทุนผลิตเนื้อหาต่ำ · ทุกวัยใช้เป็น · ไม่ต้องติดตั้ง · เครื่องสเปคต่ำเล่นได้ — **ไม่ใช่เพราะทำ 3D ไม่ได้** |
| "ทำไมไม่ใช้ Go / Vite / Express / Java Spring" | ดูเหตุผลรายตัวในหัวข้อ 11 |
| "จัดการ authorization ใน multi-tenant ยังไง" | Guard ประกาศที่ระดับ controller ทุกตัว ตรวจสอบได้จาก decorator |

## ⚠️ ประโยคที่ไม่ควรเขียน vs ควรเขียน
❌ *"ปัจจุบันการจัดงานออนไลน์มีปัญหาร้ายแรง"* (ไม่จริง กรรมการจะรู้)
✅ **แบบนี้แทน**:
> เครื่องมือปัจจุบัน (Zoom, Google Form, LINE) ทำงานได้ในระดับพื้นฐาน แต่กระจัดกระจายและไม่รองรับปฏิสัมพันธ์แบบกลุ่มย่อยที่เกิดขึ้นเองในงานออนไซต์ ระบบนี้จึงมุ่งลดต้นทุนการดำเนินงานของผู้จัด และเพิ่มโอกาสการสร้างเครือข่ายของผู้เข้าร่วมออนไลน์ให้ใกล้เคียงกับการเข้าร่วมออนไซต์

> โมเดลรายได้เป็นแบบจองความจุล่วงหน้า ทำให้ผู้จัดงานทราบค่าใช้จ่ายทั้งหมดก่อนชำระเงิน ระบบรองรับผู้เข้าร่วมเกินที่จองได้ถึง 20% และเมื่อเกินกว่านั้นจะแจ้งเตือนพร้อมตัวเลือกอัปเกรด โดยผู้เข้าร่วมส่วนเกินยังเข้าร่วมในโหมดผู้ชมได้

**"ทำให้ดีขึ้นอย่างมีนัยสำคัญ" = ข้ออ้างที่ปกป้องได้ · "แก้ปัญหาร้ายแรง" = ข้ออ้างที่โดนตอกกลับได้**

| **เม.ย. 2024** | **เพิ่งเปิด ZEP QUIZ** ← ห่างกัน 2 ปีครึ่ง |

## 4 วิธีคิดของ ZEP
1. **เริ่มจากสินทรัพย์ที่มีอยู่แล้ว ไม่ใช่จากไอเดีย** — SuperCat (กราฟิกพิกเซล + tech รองรับ traffic + ประสบการณ์ open platform จาก NekoLand) × Naver Z (know-how metaverse จาก ZEPETO) = ZEP คือจุดตัดของสองความสามารถ
2. ⭐ **เลือกข้อจำกัดเป็นกลยุทธ์** — CEO บอกเองว่า 3D ให้ความดื่มด่ำดีแต่ต้นทุนผลิตสูง และการเจาะกลุ่มอายุกว้างต้องควบคุมง่าย → **บริษัทแม่ทำ ZEPETO ที่เป็น 3D อยู่แล้ว = ทำได้แต่เลือกไม่ทำ**
3. **สร้างแพลตฟอร์มก่อน → เปิดให้คนใช้ทำอะไรก็ได้ (ZEP Script เพิ่มหลังเปิดแค่ 1 เดือน) → ดูว่าคนกระจุกตรงไหน → ค่อยทำ product เฉพาะทาง** — 110,000 space = 110,000 การทดลองที่ผู้ใช้ทำให้ฟรี
4. **วางตัวไม่ให้ชนกับ product ตัวเอง** — ZEPETO = Gen Z socializing / ZEP = work & events

## ⭐ แปลเป็นการกระทำสำหรับเรา
1. **เก็บ event log พฤติกรรมตั้งแต่ commit แรก** — ใครเดินไปไหน อยู่โซนไหนนาน คลิกอะไร ออกตอนไหน (ลง Postgres ง่ายๆ) **นี่คือตาของเรา** ถ้าไม่มี เดือนที่ 5 จะกลับมาเดาเหมือนเดิม
2. **ให้คนสร้างอะไรเองได้** — Tiled pipeline คือ ZEP Script เวอร์ชันของเรา (ไม่ใช่แค่ประหยัดเวลา แต่เป็นกลไกค้นพบ use case ใหม่)
3. **คุยกับผู้ใช้ 10 นาทีหลังใช้ทุกครั้ง** — "ตรงไหนงง ตรงไหนสนุก ตรงไหนอยากปิดทิ้ง"
4. ⚠️ **ZEP มีเวลารอ 2 ปีครึ่ง เรามี 1 ปี** → ลอกแค่**ท่าที** ไม่ใช่ timeline: สร้างของที่ใช้ได้จริงให้เร็ว เอาไปให้คนใช้จริง ปรับจากสิ่งที่เห็น ไม่ใช่จากสิ่งที่เดา
5. **พอส่วนแกนใช้งานได้ ให้รีบเอาไปใช้กับงานจริงในคณะ 1 งาน → สิ่งที่เห็นจากงานนั้นบอกว่าควรทำอะไรต่อ** แม่นกว่าการวิเคราะห์บนกระดาษ

# 20. ประเด็นที่ยังเปิดอยู่

## use case หลัก — ยังไม่เลือก (สัมมนา / career fair / open house / meetup คอมมูนิตี้)
ไม่ต้องรีบ เพราะส่วนแกนของระบบเหมือนกันหมด
⚠️ **ข้อมูล NACE (สมาคม career center สหรัฐฯ — แหล่งเป็นกลาง)**: virtual career fair หดตัวชัดเจน — ค่ามัธยฐานผู้เข้าร่วม onsite เพิ่มจาก 419→700 คน แต่ virtual ลดจาก 295→**93 คน** · ปี 2024-25: 93.9% จัด onsite / 33.2% virtual / **6.3% hybrid**
- **แต่สาเหตุคือประสบการณ์แพลตฟอร์มรุ่นแรกแย่ ไม่ใช่ปฏิเสธออนไลน์** — และ career center รายงานว่าทั้งนักศึกษาและนายจ้างต้องการปฏิสัมพันธ์แบบเจาะจงมากกว่า "5 นาทีหน้าโต๊ะ" (= สเปคของระบบคิว 1:1 เป๊ะ)
- 📌 ตัวเลข 93 คน **ตรงกับ scope 30–80 คนพอดี**
- ถ้าเลือก career fair → ต้องวางเป็น **ส่วนเสริมของงาน onsite ไม่ใช่สิ่งทดแทน** (รอบก่อนงาน / รอบต่อเนื่องหลังงาน / session 1:1 สำหรับบริษัทที่ไม่เช่าบูธเต็มวัน)
- ⚠️ ข้อมูลนี้เป็นของสหรัฐฯ — ต้องเก็บข้อมูลไทยเอง (ศูนย์แนะแนว มจธ. · HR ที่รู้จักจากที่ฝึกงาน · นักศึกษาต่างจังหวัด)
- **ประโยคที่ควรใช้ใน proposal** (เปลี่ยนข้อมูลที่ดูขัดแย้งให้เป็นเหตุผลสนับสนุน):
  > ข้อมูลจาก NACE แสดงว่า virtual career fair ในสหรัฐฯ หดตัวลงชัดเจนหลังโควิด อย่างไรก็ตาม เมื่อวิเคราะห์สาเหตุพบว่าไม่ได้เกิดจากการปฏิเสธรูปแบบออนไลน์ แต่เกิดจากประสบการณ์ของแพลตฟอร์มรุ่นแรกที่ขาดปฏิสัมพันธ์ ขณะเดียวกัน career center รายงานว่าทั้งนักศึกษาและนายจ้างต้องการปฏิสัมพันธ์แบบเจาะจงมากกว่ารูปแบบเดิม ระบบนี้จึงออกแบบมาเพื่อตอบความต้องการดังกล่าว โดยวางตัวเป็นส่วนเสริมของงาน onsite ไม่ใช่สิ่งทดแทน

### pilot จริง
งาน career day · open house · หรืองานแสดงโครงงานปี 4 ของคณะ
